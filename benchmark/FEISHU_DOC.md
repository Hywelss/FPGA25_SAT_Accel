## 一、结论

# 本板比论文慢约 25%

拆开是 **3% 时钟 + 21% 架构** —— 时钟从 230 掉到 223 MHz 占 3%，剩下 21% 是同样的活多花的周期。

依据是论文 Table 3 / Table 4 的 59 条里，**论文时间 ≥ 10 ms 且两边工作量可比的 11 条**。
两条独立路径互相印证：

| | |
|---|---|
| 时间比中位数 | 1.26x |
| 周期比中位数 | 1.21x |
| 交叉校验 | 1.205 × (230/223) = 1.243，实测 1.263，差 **1.6%** |

那 21% 定位到了 Propagation：复现论文 Table 5 后，7 个类别里 6 个的 Propagation
周期占比上升，中位数 **+7.7 个百分点**。与 HBM 多 bank 换成 NoC 单端口的预期一致。

三条附带结论：

- **覆盖率 55/59。** 丢的 4 条里 3 条是论文最慢的题（容量减半的代价），1 条论文在 U55C 上也没解出。
- **实例身份已验证。** Table 4 的 Literals / Clauses 两列 59/59 逐字对上，
  排除了"跑的不是同一批文件"。
- **有 3 条本板在跑不同的搜索**（`4blocks` 只花论文隐含周期的 15%），已从比值里剔除，机制待查。

## 二、平台对照

| 项 | 论文（U55C） | 本次移植（VCK5000） | 影响 |
|---|---|---|---|
| 板卡 | Alveo U55C（VU47P，16 nm） | VCK5000（VC1902 Versal） | — |
| Platform | `xilinx_u55c_gen3x16_xdma_3_202210_1` | `xilinx_vck5000_gen4x8_qdma_2_202220_1` | — |
| 数据时钟 | **230 MHz** | **223 MHz** | ≈ 3% 慢，可直接折算 |
| Vitis / XRT | 2022.2 / 2.14.384 | 2022.2 / 2.14.354 | 无 |
| URAM 总量 | 960（论文用 778 = 81%） | **463** | 装不下原设计 |
| 片外存储 | HBM，9 buffer 分散在 6 channel | 单个 `MC_NOC0`（DDR over NoC） | bank 并行度丢失，影响未量化 |
| `_FPGA_MAX_LITERAL_ELEMENTS` | 1,048,576 | **524,288（减半）** | literal/clause store 与 page 池同时减半 |
| `_FPGA_MAX_LEARN_ELE` | 1,024 | 1,024（未改） | 两边一致，非移植引入 |
| 求解器算法代码 | — | **一行未改** | 差异只可能来自容量与访存 |

预期差距有三个来源，必须分开归因：

1. **时钟** 230 → 223 MHz：确定的 ~3%，对所有测例一致。
2. **访存拓扑** HBM 多 bank → NoC 单端口：论文 Table 5 显示 Propagation 占 29–45% 的时间、是首要瓶颈，
   所以这一项**可能是主要差距来源**。
3. **容量减半**：不影响解得出的题的速度，只决定**哪些题解不出来**（覆盖率）。

## 六、对比结果

采集于 2026-07-23，`formind-lab-server` 的 VCK5000 @ 223 MHz DATA_CLK，59 条 × 5 次重复，
默认配置（prune 10% / reset 100 / decay 0.95 / page 16-4，与论文 §6 逐项一致）。

时间取 5 次重复的**最小值** —— 求解器确定性重放（实测周期跨度最大 1.086），
重复间差异是测量干扰不是求解器行为。

### 计时口径已验证

`totalCycleCount ÷ 223 MHz` 对实测 kernel 时间，运行 > 10 ms 的测例全部落在 **0.97–0.996**。
kernel 时间就是周期数除以数据时钟，没夹带别的。

### Table 4 / Table 3 逐条

| | |
|---|---|
| Literals / Clauses 对上 | **59 / 59**，零偏差 |
| SA 时间解出 | 55 / 59 |
| 时间比中位数（论文 ≥ 10 ms，14 条） | 1.25x |
| 时间比中位数（工作量可比的 11 条） | **1.26x** |
| 周期比中位数（同 11 条） | **1.21x** |

论文时间 < 10 ms 的行不进聚合 —— 论文只印 1–2 位有效数字，比值光靠舍入就带 ±50% 误差。

完整 59 行见仓库 `benchmark/results/paper_suite/table4_cols.md`。

**Propagation 占比 7 个类别里 6 个上升，中位数 +7.7 pp。** 这是 NoC 单端口归因的**直接测量**，
不再依赖"慢的题恰好访存重"这种间接推断。反向的 PUZZLE 只有 3 条，加权后约等于 `nqueens_32`

映射可信：`host.cpp` 的 9 个计数器里 `BACKTRACK` 全类别恒为 0，剩 8 个映射到论文 7 列，
只有 `Min|Bktrk` 是两项之和；`Allocate` 和 `Delete` 两列偏差 < 1 pp 反证映射正确。

两个副产物：**Load 占比全线下降**（SSA 24.63 → 3.62），因为存储减半后要初始化的量也减半，
装载变快，是容量减半的正面副作用；**Decide 占比全线下降**（IBM 25.02 → 7.45），
PQ 走 BRAM/URAM 不碰 DRAM，绝对开销没变，是分母被 Propagation 撑大了。

## 八、读数时必须知道的四件事

1. **取哪一列**：host metrics CSV 第 5 列（index 4）是 kernel 执行时间（秒），来源
   `host.cpp:780` 的 `executionTime/1e9`。这是与论文 "Time in ms" 口径一致的列。
   仓库 README 里说的"Column J 是 FPGA runtime"是错的，J 列是 cycle counter 百分比。
2. **论文的有效数字**：论文的 SAT-Accel 时间只印 1–2 位有效数字，印出来的 `1` 实际在 [0.5, 1.5)。
   对这种值算比值，光是舍入就带 ~50% 误差。所以汇总要报两次：全体、以及只取论文时间 ≥ 10 ms 的子集，
   **后者才是能用的那个**。
3. **`-4` 和 UNSAT 在 CSV 里都写 `0`**（`host.cpp:685` 用同一个字段），必须靠 `run_status.csv`
   的退出码区分，否则会把"跑挂了"当成"解出来是 UNSAT"。
4. **覆盖率单独统计**，不要混进速度比值里。59 条里有多少条因 `-4` / `-2` 解不出来，是独立的一个结论。
