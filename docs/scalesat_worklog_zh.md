# ScaleSAT 占用表分层：工作记录

VCK5000 上把 SAT-Accel 的片上容量墙拆掉，并把内存层次改成按访问频率划分。
分支 `vck5000-capacity-opt`，起点 `85f850d`（Phase 2，DDR 原始子句层）。

设计文档见 [`scalesat_architecture.md`](scalesat_architecture.md)（英文，含 Phase 3 完整章节）。
本文是过程记录：需求、做法、走过的弯路、以及方法论上的教训。

---

## 一、需求（按提出顺序）

1. 分析 VeriSAT 论文的策略能否用来加速 SAT-Accel
2. 做分层内存，沿仓库自己的路线图往下推，不要另起炉灶
3. **容量优先，不要太慢，不考虑 2-watched-literal**
4. 复用现有 `litStore` DMA 缓冲作 DDR 竞技场，不新增端口
5. 溢出式"容量满了再放 DDR"不算分层，要**真正的冷热分层**
6. **基本原则：利用率高的放 RAM，低的放 DDR**
7. 做 **CDCL 友好**的内存优化（用求解器自己的质量指标做放置依据）
8. 先确保加速，再做下一步
9. 周期尽可能与基线相同

## 二、当前规模上限（VCK5000）

| 项目 | 上限 | 约束来源 |
|---|---:|---|
| 变量数 | **32,768** | `_FPGA_MAX_LITERALS` |
| 子句数 | **131,072** | `_FPGA_MAX_CLAUSES` |
| 占用表元素 | **1,048,576** | URAM 524,288 + DDR 524,288 |
| 学习子句存储 | 524,288 元素 | 片上 URAM |
| 原始子句体 | 4,194,304 元素（16 MiB） | DDR 竞技场 |
| 单条学习子句 | 2,048 文字 | 冲突分析暂存区 |

**变量上限的真实含义**：每个变量有正负两条占用列表，各自补齐到 16 元素一页，
所以一个实例至少要 **32 × 出现过的变量数** 个占用元素。

- Phase 2：524,288 ÷ 32 = **约 16,384 变量**——尽管标称支持 32,768，占用表会先撑爆
- 现在：1,048,576 ÷ 32 = **32,768 变量**，与标称上限对齐

板上已验证的最大实例是 `bmc-ibm-3`（14,930 变量 / 72,106 子句 / 538,496 占用元素），
Phase 2 连 DIMACS 都载入不了，现在 1.18 秒解出。

## 三、最终的数据放置

| 数据 | 访问频率 | 位置 |
|---|---|---|
| `clsStates`（XOR 签名 + 计数器） | 每个占用条目——最热 | URAM |
| `lmd`（文字元数据） | 每次传播 | URAM |
| `cmd`（子句元数据 **+ 短子句文字**） | 每次传播 | URAM |
| 占用表常驻段 | 每次传播 | URAM（**权威**，读写都不出片） |
| 学习子句体 | 每次冲突 | URAM |
| 长原始子句体 | 每次冲突 | DDR，512-bit 突发 |
| **短原始子句体** | 每次冲突 | **不必取——已内联进 `cmd`** |
| 占用表溢出段 | 容量后备 | DDR |
| 两张位置映射表 | **只在 GC** | DDR |
| LBD 桶 | 只在 GC | DDR |

关键设计点：

- **层级由地址编码，判断只需一次比较**。不用 tag 查找——那会给每一次访问都加税。
- **放置决策放在低频时刻**：装载时（主机布局）和 GC 时（列表本来就在重写）。
- **短子句内联**：这个设计里 BCP 不读子句体（靠 XOR 签名 + 计数器），
  子句体只在冲突分析时被读，而读的是 reason 子句——短子句更容易成为 reason。
  内联把"DDR 突发读"变成"零访存"，比缓存更彻底。

## 四、实测数据

### 板上（写穿透版，`86a03f2` 构建）

| 实例 | Kissat | CaDiCaL | 基线 FPGA<br>`74694c4` | 分层 FPGA |
|---|---:|---:|---:|---:|
| nqueens_32 | 0.070 s | 0.010 s | **0.011 s** | 0.061 s |
| bmc-ibm-3 | 0.069 s | 0.141 s | **载入失败** | **1.18 s** |
| logistics-rotate-07t5 | 0.294 s | 0.593 s | 0.517 s（`-4`） | 通过 |
| marg3x3add8ch | **0.092 s** | 1.125 s | 3.54 s（`-4`） | 49.6 s（`-4`） |

### 该怎么读这张表

- **基线 FPGA 比 Kissat 快 6.4×**（nqueens_32）——SAT-Accel 那类结果是真的
- **分层当时把这个优势打掉了**（61 ms），这正是后续优化要修的
- **bmc-ibm-3 是纯粹的能力增益**：从"装不下"到"1.18 秒解出"
- **marg3x3add8ch 暴露的是算法差距**：Kissat 0.092 秒；FPGA 学了 19.8 万条子句、
  跑 49.6 秒仍未收敛。**这类实例再加容量也没用**——差在 inprocessing、
  vivification、chronological backtracking，不在内存

## 五、走过的弯路

按发生顺序。每一条都花了真实代价（一次硬件构建约 2–10 小时）。

### 5.1 我的设计错误

**A1 占用项位打包（21-bit / 24 槽）** — 功能正确（sw_emu 20 例全过），
**时序不可行**：`÷24`、`%24` 不是移位，21-bit 非对齐切片要大桶形移位器，
布线后 WNS **-27.5 ns**（基线 -0.16）。留在 `LIT_STORE_PACK` 开关后面，默认关闭。

**A3 吃空闲 URAM 扩容** — 只 +12.5%，天花板低，不是架构性改进。被否，正确。

**dataflow 反馈环** — 把缓存未命中交给同一 dataflow 区的兄弟进程处理，
两个进程互相喂数据构成环。Vitis HLS 的 dataflow **必须前馈无环**。
它干净地综合、布线、出 bitstream，然后**在板上死锁**，7 个 CU 全停在 START。

更糟的是这条路径被我设成 `FPGA_HW` 专用——**sw_emu 走的是另一条分支**，
所以这套协议的第一次执行就是在板子上。压力测试再充分也覆盖不到。

**失效的独立性断言** — 引入缓存改变了数组的别名语义：`occLine()` 把很多字
映射到同一行，于是四条 `#pragma HLS dependence variable=litStore inter false`
（原本成立）全部失效，`location_handler` 里还有两条同类。
C 仿真不做流水线，**这类失败在仿真里根本不存在**。

**写回缓存** — 教科书上对，这里是净损失：
nqueens_32 61→79 ms、bmc-ibm-3 1.18→3.87 s、marg3x3add8ch 49.6→172.5 s。
关键证据是 `BRANCH`（纯读路径，写回本不该碰）：1.37M → 5.19M。
原因：让读路径能刷新脏行，就必须去掉 DDR 指针的 `const`，
**只读 AXI master 变成读写 master**——写通道、读写仲裁、保序约束，
每一次读都付这个代价；而被测实例占用表都装得下、根本不会驱逐。

**`MAX_STREAM_DEPTH` 加大 4 倍** — 基于误读：C 仿真报告某个流达到 10,450 深度，
但 **C 仿真顺序执行 dataflow**，生产者会把整批输出写完消费者才开始，
那个数字和硬件需求无关。代价是约 12 MHz 频率。已回退。

**"装得下缓存的实例零回归"** — 我说过这句话，**实测推翻了**（5.6×）。
写穿透让每一次占用写都走 DDR，与是否命中无关。

**头文件尾部被编辑吞掉** — 替换缓存存取器时连带删掉了
`extern` 声明和 `sendTime` 原型，全线编译失败。纯粹的编辑失误。

### 5.2 最严重的方法论错误

**第一次硬件挂住时，我直接假定是自己的回归，没有先跑基线对照。**

事实是：`74694c4`（adaptation）跑得好好的，`75b34ec`（继承的 Phase 1）之后全挂——
**问题早在我接手之前就存在**。

这个假设从未被检验，导致后面几轮排查全部建立在错误前提上，
**烧掉两次 10 小时构建**。而验证只需要几分钟：bitstream 都提交在 git 里，
`git show <commit>:src/bin/workload-hw.xclbin` 取出来跑一遍即可。

### 5.3 继承的缺陷（我接手前就有，被这次工作暴露）

**Phase 1 的 `csh::STATUS` 协议** — 发一条命令、**盲读三个回复**，
而且放在冲突路径上：BCP 刚被中断，`controlSink` 在检测到冲突后仍继续转发
unit 子句 ID（那行 `&& !doBackTrack` 是被注释掉的），
所以输出流里可能还压着没人消费的长度回复。三次读吃掉残留，
真回复留在队列里，此后每次交互错位一格，直到死锁。

硬件上的相关性是**精确**的：**跑过 STATUS 就挂，没跑过就不挂**。
big20k 零冲突、从没进过回溯分支 → 通过；nqueens_32（126 次）、
bmc-ibm-3（1,714 次）→ 挂。已移除。

**Phase 2 的分配器越界** — 学习子句页分配器用 `_HOST_MAX_CLAUSE_ELEMENTS`
（4,194,304，DDR 竞技场大小）限定片上数组 `mLearnedClsStore`（524,288），
**大 8 倍**。学习子句一超过 524,288 元素就越界写 URAM。
只有学得很凶的实例才会触发，所以 nqueens_32 和 bmc-ibm-3 都没事，
logistics（UNSAT 重学习）直接踩穿。

**容量守卫少算一页** — `saveData` 每 3 元素取一次新页，`numElements` 是 3 的倍数时
最后会多取一页；而守卫按"3 元素 = 1 页"算，且 `saveData` 读分配器不检查是否为空，
`mmuStream::read()` 空池时返回**未初始化的垃圾**当页地址。已加一页余量。

**位置映射表越界** — 按 URAM-only 地址空间定尺寸，占用项一溢出就越界写。
**这个 bug 恰好只在分层真正起作用时才发作**，sw_emu 20 例全过完全没保护到。

## 六、方法论教训

1. **硬件失败先跑基线对照。** 几分钟 vs 两次 10 小时。这是本次最贵的一课。
2. **仿真跑什么，硬件就必须跑什么。** 任何 `FPGA_HW` 专用路径都是测不到的路径。
3. **HLS dataflow 必须前馈无环。** 有环也能综合布线，然后在板上死锁。
4. **引入缓存等于改变数组的别名语义**，所有依赖断言必须重新推导，不能沿用。
   HLS 对 `dependence inter false` **无条件信任，永不警告**。
5. **C 仿真的流深度是顺序执行的产物**，不反映硬件需求。
6. **HLS 按声明的 m_axi 延迟给每次迭代预留**：`latency=40` 让 II 从 1 涨到 24，
   与是否真的发生访问无关。
7. **`const` 在 HLS 里是性能属性**，不只是类型修饰——它决定生成只读还是读写 master。
8. **先查 II（几分钟）再布线（几小时）。** 这条挡下过一次 24 倍的退化。
9. **让测试真的覆盖到新路径**：`OCC_CACHE_STRESS` 把缓存缩到 64 行，
   逼小实例走完分层路径。没有它，20 例全过毫无信息量——
   那个越界 bug 就是这么溜过去的。

## 七、剩余工作

1. **验证当前版本**（`799c34d`）：地址比较 + 短子句内联 + 两张位置表下沉，
   目标是周期回到基线水平
2. **GC 里按 LBD / 活跃度决定驻留** —— 把放置策略从"分配顺序"升级为真正的热度驱动。
   GC 本来就在重写占用列表、改地址、同步位置表，增量成本小，
   且**完全不碰每次传播的关键路径**
3. **恢复子句存储遥测** —— 在 solver 本地推算（`SAVE` 返回的 `givenClsID` 够用），
   不要再用跨 kernel 的盲读往返
4. **补 SATCOMP 量级的对照** —— 现有测试实例对 Kissat 太容易（全部 0.3 秒内），
   `benchmark/` 里有真正的竞赛实例
5. **算法侧的差距** —— marg3x3add8ch 这类实例说明瓶颈在搜索质量而非内存。
   inprocessing / vivification / chronological backtracking 是另一个方向
